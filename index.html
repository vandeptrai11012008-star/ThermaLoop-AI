Workload conservation

Before and After must serve the same daily number of tasks. The existing core 60-minute benchmark is a synthetic performance envelope, not proof that all interactive SLOs pass.

∑ hourly completed work = targetDaily
Memory and serving envelope

VRAM occupancy estimated as model weights plus KV memory per 1,000 prompt tokens times concurrent sessions. Exceeding device VRAM fails feasibility; automatically adding GPUs does not solve a per-request GPU memory overflow.

VRAM_required = weights + KV_rate × context_k × concurrency
24/7 electrical cost

Installed pods remain powered all day, including when idle. Dynamic energy depends on completing all jobs; shifting work changes the time-of-use price, not the amount of work. Daylight solar is an editable assumed offset against grid purchases.

E_day = 24 × pods × P_idle + jobs × (P_run−P_idle)/rate
Important baseline boundary

Both current Before and After simulator configurations already reuse waste heat. Heat reuse potential is shown separately, NOT silently added to electricity savings. Hardware savings from right-sizing are also separate from same-fleet annual electricity savings.

C_grid = ∑ P_site,h × price_grid,h × (1−solar_h)
Failure reserve and burst margin

Baseline and optimized pod counts are sized for peak service, 24-hour job volume, reserve and the latency proxy. The optional N+1 pod has a capital cost. The failure test subtracts one pod and checks peak-serving capacity.

Fleet = operating_pods + spare_pods
Scope of financial projections

Annual savings assume every simulated day is statistically like this demonstration, pricing is static and adequate heat users exist. GPU purchase price, electricity price, solar offset and batch flexibility are placeholders. No field calibration, uncertainty bounds or market quote is implied.

Net annual change = electricity bill difference − incremental software OPEX
Scope: a hypothetical cluster built from identical 64-GPU pods. Prices and sizing assumptions are not sourced quotes. Existing 3D remains a 64-GPU *reference module* regardless of project scale.

Research caveat: the 64-GPU reference simulator is not calibrated, and its request latency or long-context serving behavior is not a validated production benchmark. The sizing layer uses explicit reduced-order proxies for burst performance, network latency, GPU VRAM and pricing. Failing a feasibility check makes a financial headline conditional—not proven deployable savings.
